### 3. Performance finding and one change kept

Profiling used `valgrind --tool=callgrind` on `bench/w_arith.sh` and
`bench/w_case.sh`, comparing fsh, oksh, dash and FreeBSD sh. The first
big surprise was not arithmetic: fsh made about 21 `alloc`/`aresize`
calls per loop iteration, and `malloc`/`free`/`realloc` were a large
part of every hot workload.

Change kept in `src/expand.h`:

```c
#define Xclose(xs, xp) ((xs).beg)
#define XPclose(x) ((x).beg)
```

`Xclose` and `XPclose` used to `realloc` every finished expansion down
to its exact used length. The containing `Area` is reset after the
command anyway, so the shrink bought nothing and cost a `realloc` per
word. Measurement:

| Workload | Before | After | Change |
| -------- | -----: | ----: | -----: |
| callgrind Ir, arith | 3,658,192,931 | 2,708,221,543 | -26% |
| callgrind Ir, case | 4,484,346,485 | 3,151,768,780 | -30% |
| wall arith, fsh | ~0.23-0.35 s | ~0.18 s | visible |
| wall case, fsh | ~0.26-0.45 s | ~0.19 s | visible |

This is an edit to an upstream file and needs a `docs/port.md` entry
(next session) and an RSS check against `docs/budget.md`.

An experimental small-block cache in `src/alloc.c` was implemented and
then **reverted**: callgrind showed it slightly *worse* (arith
2,754,534,593; case 3,195,481,875) and wall time did not improve. Do not
reapply that design without a better reason.

## Why FreeBSD sh is faster

It is not one trick. FreeBSD sh is an ash derivative; dash is also ash,
and FreeBSD is usually only modestly faster than dash in `pipe`,
`spawn`, `read` and `startup`. The large gaps are in `arith`, `case`,
`func` and `str`.

### Structural advantages of FreeBSD sh

1. **Stack/bump allocator.** FreeBSD's `memalloc.c` hands out parse and
   expansion memory from stack blocks and resets a mark. fsh's `Area`
   made a separate `malloc` per word and freed each one individually.
   Even after the shrink fix, `malloc`/`free` are still ~14-15% of
   fsh instructions in arith/case.
2. **Arithmetic is expanded in place.** FreeBSD `expand.c` calls
   `arith(start)` while expanding `$(( ))`. pdksh compiles the
   expression into an `EXPRSUB` word, then `expand()` calls
   `substitute()`, which pushes a new lexer source, lexes the whole
   expression again, and then calls the arithmetic evaluator. That
   double parse is visible in fsh `substitute`/`yylex`/`expand`.
3. **`[`/`test` is compiled as a direct parser.** FreeBSD's `bin/test`
   is a recursive-descent test parser with a fast path for the POSIX
   small-arg forms. fsh uses the generic `Test_env` callback engine
   (`ptest_isa`/`test_eval`); in the arith workload it is ~22% of fsh
   instructions vs ~11-12% for FreeBSD.
4. **Expansion is cheaper per word.** FreeBSD `argstr`/`expandarg` use
   stack space and avoid per-word allocations. fsh `expand()` is now
   ~20-28% of arith/case instructions even after removing the shrink
   realloc.
5. **Command evaluation is leaner.** FreeBSD `evalcommand` indexes
   builtins and avoids much of pdksh's `comexec`/`typeset`/`findcom`
   machinery. fsh also spends visible time in `typeset`, `getint`,
   `ktsearch` and `global` on every assignment/comparison.

### Remaining fsh hot spots after the shrink fix

From callgrind, arith:

- `expand` 540M self (19.9%)
- `evalexpr'2` 272M (10.0%)
- `free` 205M (7.6%), `malloc` 186M (6.9%)
- `getint` 171M (6.3%), `expr.c:token` 165M (6.1%)
- `alloc` 105M (3.9%), `afree` 41M, `afreeall` 33M
- `glob`/`globit` still run on expansion even when no glob chars exist

Case additionally has:

- `expand` 886M self (28.1%)
- `malloc`/`free` ~479M (15.2%)
- `do_gmatch` ~127M
- `typeset` 277M, `evalstr` 331M for 600k pattern expansions

## Next actions, in order

1. **Commit the vendor build work and the `Xclose`/`XPclose` change.**
   Add a `docs/port.md` entry (P30 or next free P number) for
   `src/expand.h`; state that it is a Linux performance edit, not a
   z/OS correctness edit. Record the measurements above.
2. **Measure RSS after no-shrink** against `docs/budget.md` (3 MB
   target). The change keeps the original 128-byte capacity instead of
   shrinking, so a busy script may hold slightly more per word until
   the command's Area is reset.
3. **Arithmetic fast path.** In `expand()`'s `EXPRSUB` case, if the
   compiled expression has no shell substitution/quoting/backtick
   syntax, call `evaluate()`/`v_evaluate()` directly instead of
   `substitute(sp, 0)`. This removes a full re-lex per `$(( ))`.
   Measure arith and func; add a regression for `$(( $x + 1 ))`,
   `${v[...]}`, quoted expressions and syntax errors.
4. **`test` fast path.** Add a direct path in `c_test()` for the
   common `[ word -op word ]`, `[ -z word ]`, `[ word ]` forms before
   setting up the generic `Test_env` callbacks. Keep `[[ ]]` on the
   existing engine. This is likely the single largest `arith` win left.
5. **Case/pattern cache or literal fast path.** `TCASE` calls
   `evalstr()` on the same literal patterns every iteration. Cache the
   expanded literal pattern in the parse node, or detect a literal
   compiled word and skip allocation. Must not cache patterns with
   `$`, `~`, brace expansion or command substitution.
6. **Revisit allocation only with a design that wins.** A global
   small-block cache was measured and lost. A stack/bump allocator
   modelled on FreeBSD `memalloc.c` is the structural answer, but it is
   a rewrite of `Area` semantics, not a quick patch.
7. **Benchmark discipline.** Use `taskset -c 0` (or equivalent), more
   than 5 runs, and record both wall time and callgrind Ir. Do not
   compare numbers from two different system-load conditions.
8. **z/OS check.** The session's changes are not built on z/OS yet.
   `bench/` targets are intentionally omitted under `FSH_ZOS`; only
   `src/expand.h` affects the z/OS binary. Run the z/OS build and
   `ctest` before committing if the change is meant to be cross-host.
